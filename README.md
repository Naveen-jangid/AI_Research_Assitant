## 1. Project Overview

Academic research papers are dense, jargon-heavy, and often formatted in ways
that make automated text processing difficult — multi-column layouts, embedded
equations, and inconsistent section headings. Researchers and students spend
significant time simply trying to understand what a paper says before they can
evaluate whether it is relevant to their work.

**AI Research Assistant** solves this problem with a full-stack AI application
that:

- Ingests one or more PDF research papers with a drag-and-drop uploader.
- Parses, cleans, and chunks the text in a layout-aware manner.
- Embeds all chunks into a local vector database for semantic search.
- Lets users have a **multi-turn conversation** with the paper, with every
  answer backed by cited page references.
- Provides **one-click expert tools**: a structured summary, a plain-English
  methodology explanation, and an annotated formula sheet — all generated by
  an LLM grounded in the actual document text.

The codebase is intentionally **modular and provider-agnostic**: changing from
OpenAI GPT-4o to Anthropic Claude or a local Ollama model requires editing a
single line in a `.env` file with no code changes needed.

## 2. Key Features

| Feature | Description |
|---|---|
| **Multi-PDF Upload** | Drag-and-drop one or multiple PDFs; all are merged into a single searchable index. |
| **Layout-Aware Parsing** | Detects and correctly re-orders two-column (IEEE/ACM-style) layouts before chunking. |
| **Smart Chunking** | `RecursiveCharacterTextSplitter` respects paragraph → sentence → word boundaries; chunks carry page-number metadata. |
| **RAG Q&A with Citations** | Every answer cites the exact source file and page number, with a collapsible excerpt preview. |
| **Multi-Turn Chat** | Up to 6 prior conversation turns are injected as context for follow-up questions. |
| **Structured Summary** | One-click generation of Overview, Key Findings, Brief Methodology, and Limitations sections. |
| **Plain-English Methodology** | Retrieves methodology sections via 4 targeted semantic queries; rewrites them as numbered steps with jargon definitions. |
| **Formula Extraction** | Regex pre-filtering + LLM analysis produces a numbered formula sheet with variable definitions. |
| **Map-Reduce for Long Papers** | Papers exceeding 80,000 characters are summarised in chunks then combined — preventing context-window overflow. |
| **Pluggable LLM Backends** | OpenAI, Anthropic, or any Ollama-served local model — configured via environment variables. |
| **Pluggable Embeddings** | OpenAI `text-embedding-3-small` or HuggingFace `BAAI/bge-small-en-v1.5` (100% local, no API cost). |
| **Pluggable Vector Stores** | ChromaDB (persistent, disk-backed) or FAISS (in-memory, ultra-fast). |
| **Download Outputs** | Every generated result can be downloaded as a Markdown file. |
| **Clear Session** | Resets all session state with a single button for a clean start. |

**Data flow summary:**

1. User uploads a PDF → `document_processor` parses pages and chunks them.
2. Chunks are embedded by `llm_handler.get_embeddings()` and stored in `vector_store`.
3. On a user question, `RAGQAChain` retrieves the top-k relevant chunks and
   passes them plus the question to the LLM.
4. The LLM answer with `[Page N]` citations is displayed in the Chat tab.
5. One-click actions follow the same retrieve → prompt → display cycle.

## 6. Installation & Setup

### Prerequisites

- Python 3.10 or higher
- `pip` (or `conda` / `uv`)
- An API key for at least one LLM provider **OR** Ollama running locally

### Step 1 — Clone the repository

```bash
git clone <your-repo-url>
cd AI_Research_Assistant
```

### Step 2 — Create and activate a virtual environment

```bash
# Using venv
python -m venv .venv
source .venv/bin/activate        # Linux / macOS
.venv\Scripts\activate           # Windows PowerShell
```

### Step 3 — Install dependencies

```bash
pip install -r requirements.txt
```

> **Note on PyTorch:** The requirements install the CPU wheel of `torch`.
> If you have a GPU and want faster local embeddings, install the CUDA wheel
> after the above: `pip install torch --index-url https://download.pytorch.org/whl/cu121`

### Step 4 — Configure environment variables

```bash
cp .env.example .env
# Open .env and fill in your values
```

Minimum required for an OpenAI setup:

```ini
LLM_PROVIDER=openai
OPENAI_API_KEY=sk-...
EMBEDDING_PROVIDER=huggingface   # free local embeddings (default)
```

### Step 5 — (Optional) Set up Ollama for fully local, zero-cost inference

```bash
# Install Ollama from https://ollama.com
ollama pull llama3
```

Then in `.env`:
```ini
LLM_PROVIDER=ollama
OLLAMA_MODEL=llama3
EMBEDDING_PROVIDER=huggingface
```

## 9. Module Deep-Dive

### 9.1 `config.py` — Configuration Management

A Python `@dataclass` (`AppConfig`) where every field defaults to a value
read from an environment variable. A module-level singleton `cfg = AppConfig()`
is created once at import time and shared everywhere via `from config import cfg`.

**Key members:**

- `cfg.active_model_name` — `@property` that returns the name of whichever
  model is currently active (e.g. `"gpt-4o-mini"`), used for display in the UI.
- `cfg.validate()` — returns a `list[str]` of error messages. Called by `app.py`
  on startup to display a user-friendly error banner instead of crashing.
  Checks for missing API keys and invalid chunk overlap settings.

---

### 9.2 `document_processor.py` — PDF Parsing & Chunking

Turns raw PDF bytes into `LangChain Document` objects ready for vector
embedding. The module has three components:

#### `PageContent` dataclass

A lightweight container for a single page's extracted text plus metadata
(`page_number`, `source` filename, `char_count`).

#### `PDFParser` class

Uses PyMuPDF's `page.get_text("blocks")` API, which returns text as a list of
positioned bounding boxes. This is fundamentally different from a flat text
extraction — it preserves spatial information about *where* text appears on
the page, which is what enables multi-column detection.

**Multi-column detection (`_is_multicolumn`):**

The heuristic computes the page midpoint and checks whether text blocks
exist in both the left half and the right half. If at least 2 blocks exist
on the right side, the page is classified as multi-column.

**Multi-column sorting (`_sort_multicolumn`):**

Blocks are partitioned into left and right groups based on which side their
horizontal centre falls on. Each group is sorted top-to-bottom independently.
The final reading order is `left_column + right_column`.

**Text cleaning (`_clean_text`):**

Four sequential transformations are applied:

1. **Unicode normalisation (NFC)** — handles accented characters from scanned PDFs.
2. **Soft-hyphen removal** (`\u00ad`) — PDFs encode word-wrap hyphens as soft
   hyphens, which appear as garbage in plain text.
3. **Hyphenated line-break re-joining** — reconnects words like `"con-\ntext"` → `"context"`.
4. **Blank-line collapsing** — three or more consecutive newlines are reduced to two.

#### `DocumentChunker` class

Uses `RecursiveCharacterTextSplitter` with a separator priority list:

```
"\n\n"  paragraph break  (highest priority)
"\n"    line break
". "    sentence end
"? "    sentence end
"! "    sentence end
", "    clause boundary
" "     word boundary
""      hard character split  (last resort)
```

Each produced chunk becomes a `LangChain Document` with metadata:

```python
{
    "source":      "paper.pdf",   # filename
    "page":        3,             # 1-based page number
    "chunk_index": 1,             # position within this page's chunks
    "total_chars": 4821,          # total characters on the source page
}
```

This metadata flows all the way to the UI where it populates the citation boxes
shown below each chat answer.

#### High-level convenience functions

- **`process_pdf(pdf_bytes, filename)`** — single call that runs
  `PDFParser → DocumentChunker` and returns `(documents, pages)`.
- **`get_full_text(pages)`** — concatenates all page texts with `[Page N]`
  markers, used by `SummaryChain` which operates on the whole document.

### 9.3 `llm_handler.py` — Modular LLM & Embeddings Factory

Decouples all other modules from any specific LLM SDK. Every other module
calls only `get_llm()` and `get_embeddings()`.

#### `get_llm(provider, temperature, max_tokens)`

A factory function that dispatches to one of three private builders:

| Backend | Builder function | LangChain class |
|---|---|---|
| OpenAI | `_make_openai_llm()` | `ChatOpenAI` |
| Anthropic | `_make_anthropic_llm()` | `ChatAnthropic` |
| Ollama | `_make_ollama_llm()` | `ChatOllama` |

Each builder imports its integration package lazily inside `try/except ImportError`,
so the app does not crash on startup if a package for an unused provider is absent.

#### `get_embeddings(provider)` — LRU-cached

Decorated with `@lru_cache(maxsize=1)` so the embedding model is loaded only
once per Python process. Sentence-transformer models can take several seconds
to load; caching ensures all subsequent calls are instant.

HuggingFace embeddings are configured with `normalize_embeddings=True` so that
cosine similarity scores are bounded to `[0, 1]` and directly comparable
across queries.

#### `stream_llm_response(llm, messages)`

A thin streaming wrapper that iterates over LLM token chunks and concatenates
them into a full string — provided as a utility for future streaming UI support.

### 9.4 `vector_store.py` — Vector Database Abstraction

`VectorStoreManager` hides whether the underlying store is ChromaDB or FAISS.
The rest of the application uses only three methods: `add_documents`,
`similarity_search`, and `as_retriever`.

#### Collection naming strategy

ChromaDB collection names must be 3–63 alphanumeric characters. The collection
name is derived from an MD5 hash of the sorted concatenation of uploaded
filenames:

```python
key    = "_".join(sorted(source_files))
digest = hashlib.md5(key.encode()).hexdigest()[:12]
name   = f"research-{digest}"
```

This ensures:
- The same set of files always maps to the same collection (cross-session
  reuse without re-indexing).
- Different file sets get isolated collections (no data contamination).

#### `add_documents(documents)`

- **ChromaDB path:** Creates a new collection on first call; incrementally
  appends on subsequent calls. Automatically persists to `CHROMA_PERSIST_DIR`.
- **FAISS path:** Creates a new index on first call; merges new documents into
  the existing index with `merge_from()` on subsequent calls.

#### `similarity_search(query, k, score_threshold)`

Returns the top-k most semantically similar chunks. When `score_threshold > 0`
and the backend is ChromaDB, low-confidence results are filtered out before
returning.

#### `similarity_search_with_scores(query, k)`

Like `similarity_search` but returns `list[tuple[Document, float]]` pairs,
allowing callers to display confidence scores alongside citations.

### 9.5 `rag_pipeline.py` — Retrieval & Prompt Chains

The brain of the application. Defines four specialised chains and typed
response data models.

#### Response Data Models

```python
@dataclass
class Citation:
    source: str        # filename (e.g. "chloride_paper.pdf")
    page: int          # 1-based page number
    chunk_index: int   # position within that page's chunks
    excerpt: str       # first 200 chars of the chunk

@dataclass
class QAResponse:
    answer: str
    citations: list[Citation]

@dataclass
class ActionResponse:
    content: str       # generated Markdown text
    action: str        # "summary" | "methodology" | "formulas"
```

#### Chain 1: `RAGQAChain` — Conversational Q&A

Retrieves the top-k chunks for the user's question, builds a message list
including up to 6 prior conversation turns for multi-turn context, and invokes
the LLM. The system prompt instructs the model to answer only from the
provided context and to append `[Page N]` after every factual claim.

#### Chain 2: `SummaryChain` — Structured Summary

Accepts the full document text from `get_full_text()`.

- **Direct mode** (≤80,000 chars): single LLM call with all text.
- **Map-Reduce mode** (>80,000 chars): split into 80K-char chunks → summarise
  each independently (Map) → combine partial summaries into final structured
  output (Reduce). This prevents context-window overflow on long papers.

The prompt enforces four exact section headings: `## Overview`,
`## Key Findings`, `## Methodology (Brief)`, `## Limitations & Future Work`.

#### Chain 3: `MethodologyChain` — Plain-English Explanation

**Problem:** Methodology sections have inconsistent headings across journals
("Materials and Methods", "Experimental Setup", "Procedure", "Apparatus", etc.).
A single keyword search misses many of them.

**Solution — multi-query retrieval:** Four targeted semantic queries are fired
against the vector store, and results are de-duplicated by their first 100
characters before being merged:

```python
METHODOLOGY_QUERIES = [
    "experimental setup methodology materials methods procedure",
    "sample preparation experimental design protocol",
    "measurement procedure testing conditions specimens",
    "data collection analysis statistical methods",
]
```

The prompt then instructs the LLM to rewrite the retrieved text as numbered
steps (`Step 1`, `Step 2`, …) with jargon definitions in parentheses and a
"Why this matters" note after each step.

#### Chain 4: `FormulaChain` — Mathematical Formula Extraction

**Two-phase approach:**

*Phase 1 — Targeted retrieval:* Four formula-oriented queries retrieve up to
4 chunks each from the vector store.

*Phase 2 — Regex pre-filtering:* A compiled regex accepts only chunks that
contain actual mathematical content:

```python
MATH_PATTERNS = [
    r"=\s*[\w\d\(\)\[\]\{\}]+",           # any equation
    r"[∑∫∂∇×·÷±√∞≤≥≠≈∝∈⊆]",            # math Unicode symbols
    r"\b(equation|formula|coefficient)\b", # keyword indicators
    r"\b(alpha|beta|gamma|delta|...)\b",   # Greek letters spelled out
    r"\^[\d\w]+",                          # exponents: x^2
    r"_[\d\w]+",                           # subscripts: C_0
]
```

*Fallback:* If no chunks pass the regex filter, the filter is dropped and
all retrieved chunks are used — preventing empty output on text-heavy papers.

The prompt produces output in a structured format:
```
**Formula 1:** J = -D (dC/dx)
**Description:** Fick's First Law — flux is proportional to the concentration gradient.
**Variables:** J = flux [mol/m²s], D = diffusion coefficient [m²/s], C = concentration, x = position
---
```

#### `build_pipeline(store)` — Convenience Factory

Instantiates all four chains at once and returns a dict stored in
`st.session_state.pipeline` so chains are reused across all interactions
without re-initialisation.

### 9.6 `app.py` — Streamlit Frontend

The UI has a sidebar for controls and a main panel with four tabs.
All state persists across Streamlit re-runs via `st.session_state`.

#### Session State Keys

| Key | Type | Purpose |
|---|---|---|
| `documents` | `list[Document]` | All chunked LangChain docs from processed PDFs. |
| `pages` | `list[PageContent]` | Raw per-page text (for Summary, which needs the full document). |
| `store` | `VectorStoreManager` | The live vector store instance. |
| `pipeline` | `dict` | The four chain objects (`qa`, `summary`, `methodology`, `formulas`). |
| `chat_history` | `list[dict]` | Each dict has `role`, `content`, and optionally `citations`. |
| `action_results` | `dict[str, str]` | Cached Markdown outputs — avoids re-generation on tab switch. |
| `processed_files` | `set[str]` | Filenames already indexed; prevents duplicate processing on re-upload. |

#### Sidebar — `_render_sidebar()`

1. Displays app title and current model/embedding provider.
2. Renders the multi-file PDF uploader.
3. On new uploads, `_process_uploaded_files()` shows a progress bar through:
   Parsing (0–60%) → Embedding (70%) → Pipeline build (90%) → Done (100%).
4. Shows a colour-coded status: green `● Ready` with file/page/chunk counts,
   or grey `● Idle` when nothing is indexed.
5. Three one-click action buttons (disabled until the pipeline is ready).
6. **Clear Session** button resets all state and triggers `st.rerun()`.

#### Chat Tab — `_render_chat_tab()`

Renders chat history as styled HTML bubbles via `st.markdown(unsafe_allow_html=True)`:

- **User messages:** right-aligned, dark blue background.
- **Assistant messages:** left-aligned, light grey background.
- Each assistant turn has a collapsible `st.expander` showing all cited
  source excerpts with filename and page number.

The input area is a `st.form` with `clear_on_submit=True` so the text box
empties after the user sends a message.

#### Summary / Methodology / Formulas Tabs

All three follow the same pattern:

1. If pipeline not ready → show an info banner with instructions.
2. If result not yet generated → show an inline trigger button as a convenience.
3. If result is ready → render the Markdown in a styled card.
4. Provide `st.download_button` to export as `.md`.
5. Provide a "Regenerate" button that clears the cached result and triggers `st.rerun()`.

## 10. How the RAG Pipeline Works

```
User question: "What is the effect of water-cement ratio on chloride migration?"
                                      │
                                      ▼
                       ┌──────────────────────────┐
                       │   Embed the question      │
                       │   (same model as indexing)│
                       └──────────────┬────────────┘
                                      │
                                      ▼
                       ┌──────────────────────────┐
                       │   Vector similarity search│
```

## 11. Prompt Engineering Details

Each chain uses a system prompt that defines three things: an expert persona,
hard operational constraints, and a rigid output structure.

### QA Prompt

```
Persona:    Expert academic research assistant
Constraint: Answer ONLY from the provided context passages
Citation:   Append [Page X] after every factual claim
Tone:       Graduate-level technical language
Anti-pad:   "Keep answers focused and avoid padding"
Fallback:   If context insufficient → say so explicitly (no hallucination)
```

The explicit fallback instruction prevents the LLM from fabricating an answer
when the retrieved chunks do not contain the needed information.

### Summary Prompt

```
Persona:    Expert academic summariser
Output:     Exactly four sections with these headings:
            ## Overview
            ## Key Findings
            ## Methodology (Brief)
            ## Limitations & Future Work
Constraint: Formal academic language; base everything on the provided text
```

The strict heading format makes the output render cleanly as Markdown and
enables future programmatic parsing if needed.

### Methodology Prompt

```
Persona:    Science communicator (plain-English expert)
Rule 1:     Replace jargon; define unavoidable terms in parentheses on first use
Rule 2:     Numbered steps: Step 1, Step 2, …
Rule 3:     Include a "Why this matters" note after each step
Rule 4:     End with a plain-English Summary section
Constraint: Do not fabricate details not present in the context
```

The "Why this matters" note was specifically designed to help non-specialist
readers understand not just *what* was done, but *why each step was necessary*
— the most common point of confusion in methods sections.

### Formula Prompt

```
Persona:    Mathematical notation expert
Output:     For each formula:
            **Formula N:** <formula in LaTeX or plain text>
            **Description:** <one-sentence explanation>
            **Variables:** <define each symbol>
            ---
Rule 1:     Include inline formulas (e.g. "coefficient D")
Rule 2:     Preserve original equation numbering if present
Fallback:   If no formulas found, state it explicitly
```

## 12. Chunking Strategy Explained

The goal of chunking is to produce text segments that are small enough to fit
many into a context window, but large enough to be semantically self-contained.

`RecursiveCharacterTextSplitter` tries each separator in order until it finds
one that produces a chunk within the target size. This means it always splits
at the most natural boundary available:

```
Example — CHUNK_SIZE=1000, CHUNK_OVERLAP=150:

Input page has three paragraphs: A (400 chars), B (700 chars), C (300 chars).

Step 1: Try to fit A + B + C = 1400 chars → too big.
Step 2: Try to split on "\n\n" (paragraph boundary).
        → Chunk 1: Paragraph A (400 chars) ✓
        → Remaining: B + C = 1000 chars — exactly at limit.
Step 3: Try to fit B + C = 1000 chars → fits!
        → Chunk 2: Paragraphs B + C (1000 chars) ✓

Chunk 2 starts 150 chars before the end of Chunk 1 (overlap)
to preserve context across the boundary.
```

The 150-character overlap ensures that a sentence spanning two chunks appears
partially in both, so a question about that sentence will retrieve at least one
chunk containing the full context.

## 13. Multi-Column Layout Handling

IEEE Transactions, ACM Digital Library, and many journal publishers use a
two-column page format. A naive PDF extractor reads blocks in document order,
which interleaves text from both columns:

```
NAIVE result (wrong reading order):
  "...the chloride concentration increased Table 1. Mix proportions
   significantly when the w/c ratio (kg/m³) was reduced below 0.5..."

CORRECT reading order (left column complete, then right):
  "...the chloride concentration increased significantly when the w/c
   ratio was reduced below 0.5... [rest of left column] ...Table 1.
   Mix proportions (kg/m³)... [rest of right column]"
```

`PDFParser._sort_multicolumn()` fixes this by:

1. Computing the page midpoint `W/2`.
2. Partitioning blocks into `left` (centre-x < midpoint) and `right` (centre-x ≥ midpoint).
3. Sorting each group independently by `y0` (top-to-bottom).
4. Concatenating: `left_blocks + right_blocks`.

The midpoint detection uses a 20px tolerance on each side to handle blocks
that slightly cross the column gutter.

## 14. Swapping LLM / Embedding Providers

No code changes are required — only `.env` edits. Restart the app after
changing `.env` to apply the new settings.

### Switch from OpenAI to Anthropic Claude

```ini
LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
ANTHROPIC_MODEL=claude-opus-4-6
```

### Switch to fully local Ollama (zero API cost)

```bash
ollama pull llama3   # one-time download
```
```ini
LLM_PROVIDER=ollama
OLLAMA_MODEL=llama3
EMBEDDING_PROVIDER=huggingface   # also free and local
```

### Switch embeddings to OpenAI (higher accuracy)

```ini
EMBEDDING_PROVIDER=openai
OPENAI_API_KEY=sk-...
```

### Switch vector store to FAISS

```ini
VECTOR_STORE_TYPE=faiss
```

> **Important:** If you change `EMBEDDING_PROVIDER` after a paper has already
> been indexed, delete the `chroma_db/` directory before re-uploading:
> ```bash
> rm -rf chroma_db/
> ```
> The stored vectors must match the model used for queries.

## 15. UI Walkthrough

### Step-by-Step Usage

**1. Upload a PDF**

Open the app at `http://localhost:8501`. In the sidebar, click "Drop PDF files
here" or drag one or more PDFs onto the uploader. A progress bar tracks:

- `Parsing <filename>…` (0–60%)
- `Embedding chunks…` (70%)
- `Building pipeline…` (90%)
- `Done!` (100%)

Status updates to: `● Ready  1 file(s) · 12 pages · 87 chunks`

**2. Ask a question (Chat tab)**

Type your question and press **Send →**. The assistant retrieves the 5 most
relevant chunks, passes them as context to the LLM, and returns an answer
with `[Page N]` inline citations. Below the answer, expand "📎 5 source(s)
cited" to see the source filename, page number, and a 200-character excerpt
from each chunk.

Ask follow-up questions freely — the last 6 turns are included as chat
history, so the LLM understands references like "What about the second
experiment you mentioned?"

**3. Generate a Summary (Summary tab)**

Click **📋 Summary** in the sidebar. The LLM produces a structured Markdown
document with Overview, Key Findings, Methodology, and Limitations sections.
Download with **⬇️ Download Summary (Markdown)**.

**4. Explain Methodology (Methodology tab)**

Click **🔬 Methodology**. The system runs 4 targeted semantic queries to find
methodology sections regardless of how they're titled in the paper, then
explains them as numbered plain-English steps with jargon defined in
parentheses.

**5. Extract Formulas (Formulas tab)**

Click **∑ Extract Formulas**. The system locates equation-heavy chunks using a
math-aware regex pre-filter, then asks the LLM to produce an annotated formula
sheet with `Formula N / Description / Variables` for each equation found.

**6. Clear Session**

Click **🗑️ Clear Session** to reset everything and start fresh.

## 16. Troubleshooting

### "Configuration errors detected" banner on startup

`cfg.validate()` found issues. Common causes:

| Error | Fix |
|---|---|
| `OPENAI_API_KEY is required when LLM_PROVIDER=openai` | Add key to `.env` or switch provider to `anthropic` / `ollama`. |
| `ANTHROPIC_API_KEY is required when LLM_PROVIDER=anthropic` | Add `ANTHROPIC_API_KEY` to `.env`. |
| `CHUNK_OVERLAP must be less than CHUNK_SIZE` | Ensure `CHUNK_OVERLAP < CHUNK_SIZE` (defaults: 150 < 1000). |

### App crashes with `ImportError` on startup

```bash
pip install -r requirements.txt
```

For provider-specific packages:
```bash
pip install langchain-anthropic   # for Anthropic
pip install langchain-ollama      # for Ollama
```

### Embedding model downloads slowly on first run

`BAAI/bge-small-en-v1.5` (~130 MB) is downloaded from HuggingFace Hub on
first use and cached in `~/.cache/huggingface/hub/`. This only happens once.

### ChromaDB error: "Collection already exists with different metadata"

Delete the `chroma_db/` directory and re-upload your PDF:

```bash
rm -rf chroma_db/
```

This usually happens when the embedding model is changed without clearing the
old index. The stored vectors become incompatible with the new model.

### LLM returns "The paper does not discuss this in the provided excerpts"

The relevant chunk was not in the top-k retrieved results. Try:

- Rephrasing the question using terminology from the paper itself.
- Increasing `TOP_K_RETRIEVAL` in `.env` (e.g. `5` → `8`).
- Reducing `CHUNK_SIZE` for finer-grained, more targeted chunks.

### Ollama returns "connection refused"

```bash
ollama serve                  # start the server
ollama pull llama3            # download the model if not already present
```

Verify `OLLAMA_BASE_URL=http://localhost:11434` in `.env`.
